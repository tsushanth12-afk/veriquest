# VeriQuest comprehensive engineering and product audit

Audit date: 2026-09-30, Asia/Calcutta. Review scope: the entire product at commit `7c644a921362aad9a680e7567e6e92fcd4e7299c`, including the completed local verdict-integrity milestone. This report is the only repository change authorized and created by this audit.

## A. Overall assessment

VeriQuest has a substantial frontend prototype and an improved, locally exercised HDL grader. It is **not ready for a dependable production MVP**. The largest remaining problems are the connection between the API and execution worker, container workspace access, authoritative accounting, and the frontend's conversion of API failures into convincing local successes. Adding more questions currently exposes additional catalog, authoring, navigation, and template limitations.

The verdict milestone is useful and should be preserved: current production parsers require a fresh execution capability, successful process evidence, complete output capture, and one consistent trusted summary. Recorded local WASM/Vite tests cover forged markers, overflow after a genuine success record, timeout, and recovery. This audit also observed a correct solution through the actual browser Run action, four correct solutions through the existing HTTP payload regression, and a successful preview evaluation. None of those exercises the production database/Celery/Docker path.

The backend contains real authorization queries, private challenge storage, progress tables, and gamification functions. Their presence does not establish that the packaged services start, dispatch work, enforce deployed database permissions, or save consistent results. Several confirmed source defects prevent trusting that path without changes and live validation.

Evidence labels used throughout:

- **Execution:** observed during this audit; the exact scope of mocks is disclosed.
- **Source:** confirmed in current code or configuration; live behavior may remain blocked.
- **Historical:** recorded in an earlier report, retained with its original limits.
- **Suspected:** a concrete source concern whose complete runtime conclusion is unverified.
- **Blocked:** prerequisites unavailable or external changes prohibited.

No confirmed new critical verdict-forgery exploit was found. The high-severity findings below are release blockers. A permission gap whose live reachability is blocked must still be closed or disproved before release.

  ├─ Supabase SDK: account/session operations
  ├─ API client → FastAPI → PostgreSQL
  │                    └─ task dispatch → Redis → Celery
  │                                              └─ DockerSandbox → host Docker daemon

### Contracts and authority

`POST /api/internal/evaluate` accepts `{challengeId, code}` and returns an `EvaluatorResult` with status, success, counts, diagnostics and runtime. It is unauthenticated, uses an in-memory 20/minute IP limit and a 65,536-byte request limit, and has no persisted scoring. Matrix requests take `{challengeId, testId}` and execute server catalog fixtures. An invalid/missing evaluator fails closed.

`POST /api/v1/submissions` accepts `{challenge_id, submitted_code, idempotency_key?}`, returns HTTP 201 with `{submission_id, status}`, and derives user identity from JWT. Poll/history responses use snake-case fields. Poll and history SQL constrain `user_id`; profile GET/PATCH constrain the authenticated subject, and PATCH allowlists display fields. Public challenge SQL selects an explicit public field list; admin routes verify privilege before reading secrets. These are positive source controls, with live authorization/RLS tests blocked.

`apiFetch` attempts one session refresh on 401. A failed retry ultimately becomes UNAUTHORIZED, including when its actual reason differs. Fetch has no AbortSignal or request deadline. The 60-second polling checks do not bound a single hung HTTP request. `WorkspaceView` uses its own async interval rather than the separate `client.ts` polling helper.

## D. Prioritized findings

Each finding has a stable ID. Severity reflects impact within intended MVP usage, not a claim that a remote exploit was executed. Recommended tests must call production components and fail their process on an unmet expectation.

### High findings

**VQ-AUD-01 — Database policies do not enforce protected columns or trusted submission creation.** Source; deployed grants and exploitation blocked. Migration `001_initial_schema.sql`, policies `profiles_update_own` and `submissions_insert_own`, checks ownership only. An own-profile update can satisfy RLS while changing XP/level/solved fields; an own-submission insert can satisfy it while supplying status/results/XP fields. The backend PATCH allowlist does not constrain direct database API access. Actual table grants were not available; private-schema naming likewise does not independently prove deployed secrecy. Trigger: a student role with the corresponding direct table privilege. Impact: tampered rankings/results and disclosure of profile metadata through broad SELECT. Correction: revoke inappropriate client privileges and define narrowly permitted display-field operations; route submission creation through server-owned logic; explicitly define private schema grants and least-privilege backend/worker roles. Acceptance: real student sessions cannot mutate protected fields, insert pregraded submissions, read secrets/other submissions, or grant roles; safe profile edits still work. Regression: live PostgREST/SQL-role tests, plus production API tests. This is a confirmed policy gap, not a confirmed deployed bypass.

**VQ-AUD-02 — Packaged backend cannot import the worker paths used for dispatch and admin validation.** Source; actual image build blocked. `docker-compose.yml` uses `./backend` as backend build context; `backend/Dockerfile` copies that context only. `backend/app/submissions/router.py:submit_solution` imports `worker.tasks.hdl_task`, catches ImportError and still returns queued. Admin `validate_challenge` imports `worker.execution` and converts failure into validation failure. The backend has no Docker socket mount either, so adding the package alone does not make synchronous sandbox validation work. Impact: submissions can stay queued and legitimate publishing cannot validate through the intended stack. Correction: explicitly publish named Celery tasks from the API without importing worker execution, use one canonical routing/app configuration, and queue admin validation. Acceptance: API image starts independently; creating a submission dispatches to `hdl_execution`; actual worker picks it up; missing broker/dispatch is visible and recoverable; admin validation reaches the worker. Regression: built-image smoke plus real broker/worker integration. Worker root-context packaging was improved historically; this separate backend packaging defect remains.

**VQ-AUD-03 — Sandbox workspaces lack daemon sharing and execution-user access.** Source; native execution blocked. `DockerSandbox._execute_docker` creates `tempfile.mkdtemp` inside the worker and asks the host daemon to bind that same absolute path. Compose shares docker.sock but no workspace volume. The directory has default private ownership, worker image runs as root, execution is forced to UID/GID 1000, and there is no ownership setup. Impact: missing input/exit files or permission errors even for correct HDL; residual sensitive material on failed cleanup. Correction: explicitly share an isolated workspace root at an identical host/worker path, establish minimum correct ownership/modes, and verify cleanup. Acceptance: native correct/wrong/syntax/timeout/overflow tests reach intended conditions; stage files are read correctly; jobs have unique workspaces; UID 1000 can access only intended data; container/workspace removal is observable. Regression: actual Docker parity and fault-injection cleanup tests. Do not relax network/capability/read-only/resource restrictions to get a pass.

**VQ-AUD-04 — Any rejected Submit can become local ACCEPTED with client XP; local state crosses users.** Execution with mocked API rejection plus real HTTP WASM; source for cross-user consequences. `submissionApi.submitSolution` ignores all structured API errors before creating a local job. The audit passed UNAUTHORIZED, FORBIDDEN, VALIDATION_ERROR, RATE_LIMITED, SYSTEM_ERROR and NETWORK_ERROR through the production adapter: all created local jobs. The unauthorized case then ran genuine WASM and returned ACCEPTED with 40 XP. This did not change server data. `getCompletedChallenges`/`recordChallengeCompleted` use origin-wide keys and a fixed public checksum; `AppProvider.awardXP` mutates `MOCK_USER`; profile fallback merges prior stats into a new identity. Logout does not reset these ledgers. Matrix fixture execution can also mark a challenge locally complete without student code. Impact: access/rate-limit failures look like scored success, wrong-user displayed stats, suppressed/duplicated demo awards, and misleading “Server progress updated” messages. Correction: explicit demo mode with isolated unscored state; authenticated scoring must surface API errors; scope/reset caches and invalidate pending work on identity changes; disable production matrix scoring. Acceptance: 401/403/422/429/5xx do not create scored local jobs; A/logout/B never inherits A's progress; server XP alone updates authenticated stats. Regression: production adapter error matrix plus browser two-user/logout and slow-profile tests.

**VQ-AUD-05 — Quest awards repeat and profile/leaderboard totals can diverge from the ledger.** Source; live transactions blocked. `xp.py:check_quest_completion` inserts a bonus whenever the quest is complete, with no quest ID award record, uniqueness, or previous-award check. It is called even after `award_xp` returns zero for an already-completed challenge. `idx_xp_transactions_unique_challenge` excludes null challenge IDs, so it does not protect quest rows. `award_xp` sums and saves profile XP before the quest insertion; repeated acceptance can keep adding quest bonuses without updating the profile. The progress row lock covers one challenge, not simultaneous different-challenge awards for one profile; cached profile XP can also lose a concurrent aggregation. Badges read the stale profile, global ranking uses profile XP, weekly/monthly use ledger sums. Correction: unique user/quest completion records; one transaction/locking policy for awards and profile reconciliation. Acceptance: first completed quest awards once; repeats/retries/concurrency award zero extra; profile XP/level equals ledger aggregate after challenge and quest rewards; concurrent different solves cannot lose XP. Regression: real PostgreSQL sequential/concurrent award and rollback tests, including existing-data reconciliation planning.

**VQ-AUD-06 — Attempts are counted twice or penalize infrastructure failures.** Source; live accounting blocked. `submissions/service.py:create_submission` increments progress attempts before dispatch. `_execute_hdl_submission` increments again for wrong_answer/compilation_error/timeout, while its infrastructure branch only logs zero penalty without undoing the initial increment. `award_xp` increments profile attempts only for a first award; repeated accepted results do not increment that profile value. Impact: inconsistent attempts/acceptance rates, apparent student penalties for outages, disagreement between profile and per-challenge progress. Correction: one explicit authoritative accounting decision keyed to a finalized submission and its `counts_as_attempt`; transactional and retry-safe. Acceptance: every qualifying terminal attempt counts exactly once; system/configuration errors count zero; repeat accepted submissions follow the documented policy consistently; aggregate and challenge totals agree. Regression: production task/service tests with live DB, retries and infrastructure errors.

**VQ-AUD-07 — Job ownership, retries, idempotency and terminal accounting are not atomic.** Source; concurrent execution blocked. `_execute_hdl_submission` selects queued then updates compiling without a locked/conditional claim. It saves accepted/completed_at before entering the gamification transaction. A poll can stop at accepted with zero XP; a subsequent gamification exception rewrites system_error. Inner exception handling consumes most failures, so the outer Celery retry rarely sees them. Late-ack worker death after claiming leaves a nonqueued job that redelivery ignores. `create_submission` is not transactional, the idempotency index is nonunique, concurrent requests can both create, and the router redispatches `is_duplicate` results. No stuck-job reaper/outbox exists. Correction: atomic claim, unique per-user request keys, transactional creation/dispatch recovery, retry-safe finalization with terminal results visible only after accounting commit, and a bounded stuck-job policy. Acceptance: duplicate requests/delivery produce one execution/finalization; killing a worker recovers or truthfully finalizes a job; accepted is immutable and includes finalized award evidence. Regression: live concurrent API/DB/queue tests and worker-loss fault injection.

**VQ-AUD-08 — Admin frontend fabricates success and ignores real created IDs.** Source; anonymous admin page verified in browser, mutating operations not executed. `AdminView.handleCreateOrUpdate`, `handleValidate`, `handlePublish`, `handleUnpublish` treat NETWORK_ERROR/caught exceptions as local success. Validation claims clean compilation and 100% assertions without execution. Create discards the server's returned challenge_id even on success and constructs `ch_<timestamp>`, so subsequent operations can target an invalid UUID. Local authoring changes disappear after reload. Sidebar/mobile expose admin to anonymous users and App routing does not gate it; backend role checks still constrain real API access. Correction: use server results/IDs and show errors without lifecycle mutation; gate privileged UI from authoritative role data; any demo authoring must be explicitly labeled and unable to publish. Acceptance: network rejection never displays validated/published/saved; successful create uses returned UUID; reload and subsequent edit/validate/publish reference the same row; students see no privileged controls. Regression: production UI/adapter tests for success IDs and all failures, plus actual authorized admin workflow.

**VQ-AUD-09 — Validation is not bound to a challenge revision or executed configuration.** Source; live lifecycle tests blocked. Admin `update_challenge` writes public/private data without one transaction; the secret-change trigger invalidates only solution/testbench changes, not execution_profile/evaluator_type/interface changes. `validate_challenge` synchronously executes while holding a connection, ignores the stored execution profile, sets validation status without clearing is_published, and can violate `published_requires_published_status` when called for a published challenge. Publication reads validated then updates without revision comparison; an edit or concurrent validation can race. Unpublish changes only is_published while returning draft, leaving validation_status published. Prerequisite IDs in schemas are not persisted. Correction: versioned transactional lifecycle and queued validation of a snapshot; enforce validation configuration/interface consistency; invalidate relevant edits; make unpublish/archive transitions truthful. Acceptance: editing a validated/published revision cannot reuse stale validation; public/secret edits commit together; published challenge revalidation has a defined successful path; state returned matches DB; authoring prerequisites work if retained in scope. Regression: live revision/edit/validate/publish races and rollback tests.

**VQ-AUD-10 — CI cannot substantiate its advertised security and production regression gates.** Source and execution of available suites; full Python gate blocked. `npm test` runs 23 mostly reimplemented/mock checks. `backend_multiuser_security.test.mjs` similarly mocks identity, DB and XP. Backend tests import absent `LEVEL_THRESHOLDS`, `normalize_evaluator_output`, `EvaluatorResult`; AST inspection confirmed their absence. Fixtures pass unsupported AuthenticatedUser `is_admin` and outdated Settings fields; expected level titles/thresholds conflict with production. CI's “No Secrets in Frontend Bundles” job greps public types, builds no bundle, and does not inspect emitted assets or runtime responses. New production verdict/HTTP regressions are not wired into CI. `test_regression_test_matrix` reports verdict mismatches without setting failure exit; `test_real_iverilog` prints outcomes without assertions; chunked payload test permits a socket-error branch without a confirmed 413. Correction: repair tests against current production APIs, strengthen assertions, run meaningful protocol/HTTP regressions and real bundle checks, then add service/container/database gates. Acceptance: intentional production regressions cause CI failure; backend tests collect and execute; job names accurately describe scope; all ten verdict attack categories remain enforced. Regression: deliberately failing expectation checks and CI run in the actual supported runtime. Passing current mocks is not live security evidence.
